Anthropic 与 OpenAI 如何构建内部产品开发流程

Bevisy · 2026 年 11 月 · 基于双方公开发表材料整理

一句话概括：两家公司都把内部开发重构为「agent 优先」的管道——人负责意图、验收与最终拍板，agent 在隔离沙箱中并行实现并通过自动化验证回路自检，代码经由分支/PR 合入；Slack、issue、CLI 只是入口的差异，核心是同一条「spec → 并行 agent → 自动验证 → 分层人审」的流水线。

文中所有效果数字（65%、99.8% 等）均为公司自报数据，口径详见第五节。

一、共同范式

剥离入口差异后，两家内部的开发流程是同构的。人的角色从「写代码」移动到管道两端：左端定义意图与验收标准，右端做风险分层后的最终审阅；中间的实现、测试、初审交给并行运行的 agent。

这条管道有两个容易被忽略的支撑点：

① 反馈回路是效率的核心来源。Claude Code 创始人 Boris Cherny 反复强调给 agent 一条可执行的验证命令（测试、build、浏览器实测），可让产出质量提升 2–3 倍；OpenAI 内部的 PR 驱动方式则被官方文章直接描述为 "effectively a Ralph Wiggum Loop"——agent 自审、互审、迭代到通过为止。[6][10]

② 知识必须进 repo，不能留在聊天里。OpenAI 的说法是 "what the agent can't see doesn't exist"：Slack 消息、Google Docs、口头约定都被明确列为 agent 看不见的知识，做法是把一切编码成仓库内 markdown；Anthropic 的 CLAUDE.md 与 skills 体系同理。[10][6]

二、Anthropic：Claude Code 为核心，Slack 作组织级入口

2.1 工程层：终端与云端并行 session

Anthropic 官方发布的《Claude Code Best Practices》给出了被内部广泛采用的工作流：explore → plan → code → commit——先让 agent 读代码库，再进 plan mode 把方案打磨到可一次性执行，然后才写码，最后用测试、截图、浏览器实测等反馈回路验证。[6]

创造者 Boris Cherny 的个人用法是典型样本：本地终端 5 个独立 checkout、claude.ai 网页端另开 5–10 个云端 session 并行推进，约 10–20% 的 session 会中途放弃；他自述借此每天合并 20–30 个 PR，而团队的重心是 code review 与 steering——「工程师读到 PR 时，代码已经处于良好状态」。[7][12]

Claude Code 自身超过九成的代码由 Claude Code 编写，团队靠内部 dogfooding 频道（每 5–10 分钟一条反馈）驱动快速迭代。[12][5]

2.2 组织层：从 Claude in Slack 到 Claude Tag

2026 年 6 月 23 日，Anthropic 发布 Claude Tag：Claude 以团队成员身份常驻 Slack 频道，任何人在任意 thread 里 @Claude 即可委派任务。机制上，每个 thread 绑定一个独立的一次性云端沙箱（运行与 Claude Code on the web 相同的引擎），可 clone 仓库、修改代码、推送分支或开 PR；频道内所有人对同一 session 接续 steer；每个频道有独立的 agent identity 与记忆，权限由管理员按频道划定。旧的 Claude in Slack 应用于 2026 年 8 月 3 日强制迁移。[1][3][4]

发布稿称：「在频道里 @Claude 已是我们完成工作的主要方式之一。今天，我们产品团队 65% 的代码由内部版 Claude Tag 创建。」同一场发布中，官方 webinar 页面的表述是「打开约 65% 的 PR」，而 Fortune 转述产品负责人 Cat Wu 的说法则是「审批并合入产品团队提交的 65% 代码变更」——同一时期、同一公司，出现了创建 / 打开 / 审批三种口径，详见第五节。[1][2][4]

值得注意的是覆盖面：Claude Tag 的日常使用者横跨工程、GTM、支持与数据科学——Slack 入口承接的是「上下文已经在聊天里」的任务（bug 报告、客户反馈、数据取数、法务审核），而非核心工程编码本身。[2][3]

2.3 规模后果：自建源码管理与评审系统

agent 化开发把合并量推到了为人类设计的工具无法承受的地步。据 Anthropic 工程博客：2026 年 5 月 monorepo 平均每天合入约 2,500 个代码变更，到 9 月已超过 30,000 个/日；主分支历史近 100 GB，每天为 CI 执行约 2,500 万次代码检出。为此他们在五个月内自建了服务端源码管理系统 Scion（并整体迁离 git）与代码评审界面 Antique。[5]

三、OpenAI：Codex 为核心，Slack 作全公司操作系统

3.1 沟通层：一切都在 Slack 上

前员工 Calvin French-Owen（2024.5–2025.6 在职，Codex 发布团队成员）离职后写道：「一切，真的一切，都跑在 Slack 上。没有邮件。我在那里的整个时间大概只收到过 10 封邮件。」Slack 不是可选工具，而是公司唯一的协作面——这构成了后文所有 agent 入口选择的前提。[9]

3.2 工程层：Codex 全家桶与「IDE 的退场」

Codex 起点是 2024 年底 OpenAI 内部立项的 aSWE（Autonomous Software Engineer）目标——Greg Brockman 与 Sam Altman 直接拍板「该有一个自主软件工程师与我们并肩工作」。此后 Codex CLI（2025-04）、Codex in ChatGPT（2025-05）、桌面 App（2026-02/03）、ChatGPT Work（2026-07）相继落地；2025-10-06 GA 时即附带 Slack 集成：@Codex 在频道或 thread 里被 @ 即承接任务。现入口多为 @ChatGPT，仓库类工作转交 Codex Cloud 任务执行、结果回帖。[8][12][11][14]

内部使用强度（均为公司自报）：

指标数值来源

副作用同样公开：2026 年 1 月起 IDE 使用率下降；部分 CI/CD 系统负载约 10 倍增长；PR/代码评审流程「开始裂开」，公司正在重新设计评审与部署——包括多视角 agentic review 与「护送变更到生产」的监控 agent。[11]

3.3 自动化工厂：把反馈回路做成常设系统

OpenAI 内部构建了若干常设的 agentic 反馈回路：Perf Factory 监控生产性能并自动派出 Codex agent 修复性能问题；Sevbot 是常驻事故 Slack 频道的应急 agent，自动收集上下文、提出缓解方案但绝不自主执行，工程师可指令其实施特定缓解。文档则全部移入源码库，Codex 的上下文接入 Git/GitHub、Slack、Notion、Databricks、Datadog 与内部日志——新员工入职被告知「任何问题先问 Codex」。[11]

3.4 Harness engineering 实验：0 行手写代码的产品

2026 年 2 月，OpenAI 发表内部实验总结：一个三人团队从空仓库出发，五个月构建了内部 beta 产品，约 100 万行代码全部由 Codex 编写、0 行人工手写，期间开合并约 1,500 个 PR（人均 3.5 个/日），单次 agent 运行可超 6 小时。经验要点：失败几乎从不靠「更努力地重试」解决，而是问「agent 缺什么能力，如何让它可见、可执行」；计划（execution plans）作为一等工件入库；文档由专职 doc-gardening agent 维护；给 agent「一张地图，而不是 1,000 页说明书」。[10]

五、数据口径与常见误读

整理公开材料时，有三类表述需要格外小心：

① 同一数字、多种口径。围绕「65%」存在三个并列的官方表述：

出处原文表述实际含义
发布稿 [1]"65% of our product team's code is created by our internal version of Claude Tag"代码创建
官方 webinar 页 [2]"opens roughly 65% of our pull requests"打开 PR
Fortune 转述 Cat Wu [4]"approving and incorporating 65% of the code changes the product team submits"审批并合入变更

「创建代码」「打开 PR」「审批并合入」是三件不同的事，传播中常被混用为「AI 写了 65% 的代码」。本文按原出处分别标注。

② 主场数据。所有效果数字均为公司自报、来自全球最 AI 原生的工程环境（工具作者自用），不宜直接外推为行业基准。

③ 分母不明。多数百分比未说明分母（行数？提交？PR？功能？），阅读时应保留这个缺口。

七、可迁移的观察

以下为基于上述材料的归纳，供参考：

1. 入口跟随上下文，而不是相反。上下文在聊天里的任务走聊天入口（Slack），有明确验收标准的任务走 issue/PR——两家都是双轨并行，而非「Slack 驱动一切」。

2. 反馈回路优先于模型选择。可执行的验证命令（测试、build、浏览器、监控查询）是 agent 产出质量的最大杠杆，两家都把它做成了常设系统。

3. repo 是唯一事实源。AGENTS.md/CLAUDE.md、仓库内文档、执行计划、evals 全部入库并由 agent 自维护；聊天记录不承担知识沉淀职能。

4. 瓶颈会转移。编码自动化后，先饱和的是评审与 CI/基础设施——两家分别以 Antique/Scion 与 review 重构应对。规划 agent 战略时应把这部分算进成本。

5. 人的岗位收缩到两端。定义意图与验收、风险分层后的最终拍板；中间的实现-测试-初审链条交给并行 agent 与自动验证。
